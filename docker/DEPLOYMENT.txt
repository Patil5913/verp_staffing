VERP STAFFING - DEPLOYMENT GUIDE
================================
Image: parthpatil5/verp_staffing (Docker Hub, private)
Contains: frappe v15 + verp_staffing + vruglechat (chat is baked in but NOT
installed on any site until you run add-app.sh).
One image, many tenants: each tenant = one Frappe site named after its domain.
Two ways to run it: FOLDER 2 (one stack, same code for all tenants) or
FOLDER 4 (one stack per client, custom code per client, shared MariaDB).

NEVER: run "docker compose down -v" (deletes all data), or paste tokens /
passwords into chat or tickets.


-----------------------------------------------------------------------
FOLDER 1: docker/build/     (build + publish the image; needs Docker)
-----------------------------------------------------------------------
Needs: a Gitea access token with read access to verp_staffing and vruglechat,
       and a Docker Hub login (access token).

  docker login -u parthpatil5
  cd docker/build
  GIT_TOKEN=<gitea token> ./build.sh v0.1.2      # builds + pushes :v0.1.2 and :latest

Branches baked in are listed in build/apps.json (edit there to change).
The build is slow (frontend build); allow ~3 GB RAM. Push code to git first:
the image is built from git, not from local files.


-----------------------------------------------------------------------
FOLDER 2: docker/deploy/     (run the stack + create sites on a server)
-----------------------------------------------------------------------
First time:
  docker login -u parthpatil5
  cd docker/deploy
  cp .env.example .env         # set IMAGE=parthpatil5/verp_staffing:<tag>,
                               #     DB_PASSWORD=<strong password>, HTTP_PORT=<port>
  docker compose up -d
  docker compose ps            # all Up; "configurator" Exited (0) is normal

Create a tenant (site) with the local DB:
  ./create-site.sh tenant1.example.com         # prints the Administrator password - save it

Install chat on ONE tenant (optional):
  ./add-app.sh tenant1.example.com vruglechat

Publish a tenant on the internet (host nginx + certbot, run as root on the host;
the domain's DNS must already point at this server):
  sudo ./host-nginx-site.sh tenant1.example.com <HTTP_PORT>
  Then open https://tenant1.example.com/verp

Health check for a tenant:
  curl -s -H "Host: tenant1.example.com" http://localhost:<HTTP_PORT>/api/method/ping
  -> {"message":"pong"}

Upgrade to a new image:
  # set the new tag in .env, then:
  docker compose pull && docker compose up -d
  ./migrate-all.sh             # migrates every tenant

Backups (DB + files, all tenants; stored in the sites volume):
  ./backup.sh

Useful:
  docker compose logs -f backend          # or frontend, configurator, scheduler ...
  docker compose exec backend bench --site all enable-scheduler
  docker compose exec backend bench --site <site> set-admin-password <new>
  docker compose restart backend


-----------------------------------------------------------------------
FOLDER 3: docker/deploy/client-db/    (database on the CLIENT's server)
-----------------------------------------------------------------------
Use when a client wants their MariaDB on their own server. The app stack stays
on our server. Files/attachments and backups still stay on OUR server.

On the CLIENT server:
  cd docker/deploy/client-db
  cp .env.example .env         # set DB_ROOT_PASSWORD and BIND_ADDRESS (VPN/private IP)
  docker compose up -d
  ufw allow from <OUR_SERVER_IP> to any port 3306 proto tcp    # only our server

On OUR server (from docker/deploy):
  docker compose -f docker-compose.yml -f docker-compose.remote-db.yml up -d
  ./create-site.sh client.example.com --db-host <client-vpn-ip> --db-port 3306
  # asks for that client's MariaDB root password

Do NOT expose MariaDB to the public internet: use a VPN/private link (and TLS).


-----------------------------------------------------------------------
FOLDER 4: docker/shared/ + docker/deploy/client.sh   (MANY CLIENTS, custom code)
-----------------------------------------------------------------------
Use when clients need DIFFERENT code (e.g. a client/<name> branch). Frappe
shares code per bench, so each such client gets its own image and its own
lean compose project, while ONE MariaDB is shared to save RAM.

  shared MariaDB (verp-shared-db, network verp_shared)   <- one, for all
  project "acme": backend, frontend, websocket, scheduler, worker, redis
  project "beta": backend, frontend, websocket, scheduler, worker, redis

Each site has its own database + DB user inside the shared MariaDB.
Per-client footprint is reduced: 2 gunicorn workers (GUNICORN_WORKERS),
one worker for all queues, one redis capped at 128 MB (cache + queue).
Trade-off: a restart of verp-shared-db affects every client.

1) Once per server - start the shared DB:
  cd docker/shared
  cp .env.example .env         # set DB_PASSWORD; INNODB_BUFFER_POOL_SIZE (default 1G)
  docker compose up -d

2) Build the client's image (see FOLDER 1). Point build/apps.json at the
   client's branch and use a client-specific tag, e.g. acme-1.0.0.
   NOTE: build.sh also pushes :latest - do not let a client build overwrite
   the tag other clients use; deploy by the explicit client tag.

3) Per client - env file and start:
  cd docker/deploy
  cp clients/example.env clients/acme.env
       # IMAGE=parthpatil5/verp_staffing:acme-1.0.0
       # HTTP_PORT=8081        (unique per client)
       # GUNICORN_WORKERS=2
  ./client.sh acme up
  ./client.sh acme create-site acme.example.com     # prints Administrator password
  sudo ./host-nginx-site.sh acme.example.com 8081   # publish (DNS must point here)

client.sh commands (client = name of clients/<client>.env; also the -p project):
  ./client.sh <client> up                      start / apply env or image change
  ./client.sh <client> down                    stop (volumes kept, never use -v)
  ./client.sh <client> logs [service]          follow logs
  ./client.sh <client> create-site <domain> [admin-password]
  ./client.sh <client> add-app <site> vruglechat
  ./client.sh <client> migrate                 migrate every site of that client
  ./client.sh <client> backup                  DB + files, into that client's sites volume
  ./client.sh <client> bench <args...>         any bench command

Update ONE client (others keep running):
  # set the new IMAGE tag in clients/acme.env, then:
  docker login -u parthpatil5
  ./client.sh acme up
  ./client.sh acme migrate

Health check:
  curl -s -H "Host: acme.example.com" http://localhost:8081/api/method/ping

Notes:
- The older single-stack files (docker-compose.yml, create-site.sh,
  migrate-all.sh, backup.sh, add-app.sh) are for ONE all-in-one deployment;
  do not mix them with the client stacks on the same server.
- Backups are stored per client in its sites volume; the shared DB volume
  (verp_shared_db-data) holds all client databases - snapshot/dump it too.


-----------------------------------------------------------------------
SECURITY NOTES
-----------------------------------------------------------------------
- Containers have no passwords; whoever can run "docker" on the host can enter
  any container. Restrict SSH and the "docker" group.
- App containers run read-only with dropped privileges (frontend/nginx and db
  are the exceptions).
- MariaDB root password = DB_PASSWORD in docker/deploy/.env (single stack) or
  docker/shared/.env (shared DB). Neither is in git.
- Each tenant has its own Administrator password (printed once by create-site.sh).
